### <a name="_qmphm5d6rvi3"></a>**Решение**  
Приведите диаграммы контекста и контейнеров в модели C4. Опишите основные компоненты и интеграции всех элементов решения.

[CD диаграмма](/Task3-CD.drawio.png)

[C2 диаграмма](/Task3-C2.drawio.png)

1. Колл-центры: неизвестны поддерживаемые внутренним колл-центром протоколы. С учётом используемых технологий (Java Spring Boot) предполагается интеграция по REST HTTPS API (отправка заявки в колл-центр на звонок клиенту, получение обратной связи от колл-центра по обработке обращений).  
2. Для обеспечения требований 10, 5, 4, 3 предложено создание отдельной процессинговой подсистемы "Система онлайн обслуживания".  
3. Для требования 11 функциональность работы со ставками и процесс согласования заявок реализуются в интерфейсе АБС, что позволит организовать единое окно для сотрудников без необходимости переключения между системами.  
4. Для работы со ставками и согласованием заявок предусмотрена интеграция интерфейса АБС и "Подсистемы онлайн обслуживания". При реализации новых интерфейсов АБС будет делать обращения к новой системе: Use Cases 1.2, 1.2.1, кроме п. 3.  
5. Процесс получения ставок для клиентов создаст высокий RPS (более 1000). Для обеспечения требования 6 спроектирован отдельный микросервис со своей БД для работы со ставками. Менеджеры бэк-офиса просматривают и устанавливают ставки через интерфейс АБС с помощью микросервиса. Для синхронизации данных микросервис отправляет запрос в сервис abs-synchronization.  
6. Анализ данных для принятия решения по ставке остаётся не изменённым и работает на АБС (например, при клике по клиенту в новой системе данные загружаются из АБС по старому процессу в рамках MVP).  
7. Для требований 1, 2 используется протокол HTTPS.  
8. Для требований 3, 4 предусмотрено равномерное горизонтальное масштабирование и распределение запросов между серверами, приложениями и ЦОД.  
9. Для нотификации клиента по SMS о статусах заявок создан отдельный микросервис (требование 9).  
10. Для двухфакторной аутентификации в интернет-банке реализован специальный микросервис, интегрированный с SMS-шлюзом (MVP-решение).  
11. "Подсистема онлайн обслуживания" должна быть развернута минимум в 2 ЦОД-ах для обеспечения доступности.  
12. Для работы с депозитами в интернет-банке предложен отдельный микросервис для обеспечения горизонтальной масштабируемости и изоляции от основного монолита платежного сервиса.  
13. Для авторизации действий в интернет-банке предложен отдельный микросервис для масштабируемости и безопасности (отдельная БД с механизмами шифрования, доступ только внутри контура).  
14. Для обеспечения требования 14 по разделению доступа к данным, взаимодействие с сервисами реализовано через API Gateway, который обеспечивает проверку ролевой модели и обогащение запросов нужными авторизационными данными

### <a name="_bjrr7veeh80c"></a>**Альтернативы**  
1. Кэширование можно было бы реализовать на уровне подсистемы онлайн-обслуживания:  
  - Плюсы: удобное управление валидностью кэша (реакция на изменения статусов заявок, ставок).  
  - Минусы: длинная цепочка запросов от UI интернет-банка через back internet-bank → API GW → request_service → cache не позволит обеспечить требуемый отклик.  
2. При отсутствии компетенций в Redis можно использовать in-memory кеш в сервисе:  
  - Плюсы: использование существующих навыков, отсутствие доп. инфраструктуры.  
  - Минусы: проблемы с консистентностью данных при обращении к разным инстансам.  

Задачи для целевой архитектуры на расширение:  

- Отдельная система аутентификации, авторизации и второго фактора.  
- Отдельная система/группа компонентов для отправки SMS-коммуникаций клиентам с поддержкой ретраев.  
- Микро-фронтенд для интернет-банка.

### **Недостатки, ограничения и риски**  
1. Аутентификация в интернет-банке — небезопасное и сложно масштабируемое решение. Для снижения риска необходимо спланировать проектирование отдельной системы аутентификации, авторизации и двухфакторной аутентификации для клиентов.  
2. Процесс загрузки документов и открытия депозитов по заявкам остаётся в AS IS АБС; для оптимизации требуется отдельное проектирование.  
3. Интернет-банк интегрирован с SMS-шлюзом по HTTPS; риски: при недоступности шлюза интернет-банк должен реализовать механизмы отказоустойчивости. Специализированная группа компонентов могла бы взять эту функциональность на себя.  
4. Единый фронтенд интернет-банка несёт риск снижения доступности при перегрузках.
